## 1. Executive Summary

Кодовая база зрелее, чем типичный «MVP-мессенджер». Подтверждено по коду наличие нетривиальных
механизмов, которые обычно отсутствуют: персистентный outbox в IndexedDB, идемпотентность
отправки через `@@unique([chatId, clientMessageId])` с обработкой гонки P2002, forward-sync для
залечивания разрывов, Socket.IO Redis-adapter + межсервисная доставка через Redis pub/sub
(т.е. код **готов** к multi-instance), presence в Redis, perfect-negotiation и корректный teardown
WebRTC-ресурсов, временные TURN-креды (HMAC).

Однако к запуску на сотни тысяч пользователей система **не готова**. Главные причины:

1. **Деплой single-instance / single-host** — код умеет масштабироваться, инфраструктура нет
   (по одному контейнеру каждой роли, одиночные Redis/PG/MinIO = SPOF).
2. **`KEYS presence:*` на каждом подключении сокета** — лавинная деградация Redis при
   реконнект-штормах (а на Redis завязано всё realtime).
3. **Зависшие звонки и вечный BUSY** — таймеры дозвона в памяти инстанса + RINGING-стейт с TTL 4 часа.
4. **Медиа целиком буферизуется в RAM + транскод инлайн в HTTP** без очереди и лимитов — OOM/CPU-saturation.
5. **Outbox без backoff и без лимита попыток** + повторная заливка файлов при ретрае — шторм ретраев и orphan-объекты.

**Вердикт готовности: NOT READY для масштаба сотен тысяч. READY для закрытой беты / низкой
конкуренции (сотни одновременных) после устранения CRITICAL по звонкам и presence.**

## 2. Общая оценка готовности

| Домен | Оценка | Комментарий |
|------|--------|-------------|
| Отправка сообщений (надёжность доставки) | 🟡 Средне | Идемпотентность и outbox есть; нет backoff, неполные статусы, FIFO не гарантирован |
| Медиа-пайплайн | 🔴 Слабо | Буфер в RAM, транскод в HTTP-цикле, orphan-файлы, рассинхрон лимитов |
| Звонки (1:1) | 🟡 Средне | Механизмы есть; неатомарные переходы, зависшие звонки, нет ICE-restart |
| Звонки (группа) | ⚫ Нет | `CALL_GROUP_UNSUPPORTED` — честная заглушка (Phase 2) |
| Масштабируемость | 🔴 Слабо | Код готов, инфраструктура single-instance |
| Отказоустойчивость | 🔴 Слабо | SPOF на Redis/PG/MinIO, нет graceful shutdown, нет локов в воркере |
| Realtime-доставка | 🟢 Хорошо (архитектурно) | Redis adapter + pub/sub; узкое место — `KEYS` и глобальные presence-бродкасты |

## 3. Архитектурные риски

- **R1. Инфраструктура отстаёт от кода.** Redis adapter и pub/sub подключены
  (`socket.server.ts:143`, `:310`), но `docker-compose.yml` запускает ровно по одному инстансу
  каждой роли без балансировщика и без `deploy.replicas`. Потенциал масштабирования не реализован.
- **R2. Redis — центральный SPOF.** Adapter + pub/sub-доставка + presence + rate-limit. Падение =
  остановка realtime; pub/sub не персистентен → опубликованные в момент сбоя сообщения теряются
  (залечиваются только pull-ресинком при открытии чата).
- **R3. Тяжёлые задачи в синхронном пути.** Транскод видео, Whisper-транскрипция, AI `/ask`,
  push-рассылка офлайн-членам — всё выполняется инлайн в HTTP/socket-обработчике без очереди,
  лимита конкурентности и таймаут-бюджета.
- **R4. Состояние жизненного цикла звонка хранится частично в памяти процесса** (`ringTimers`)
  при включённом multi-instance adapter — несогласованность при реконнекте/рестарте.
- **R5. Нет компенсирующих транзакций между MinIO и БД** — загрузка файла и создание `Attachment`
  это два независимых запроса; сбой между ними даёт orphan-объект (без GC) или потерянное уведомление.

## 4. Найденные проблемы (подтверждены по коду)

Все находки ниже верифицированы прямым чтением файлов.

### Сообщения / outbox
- Нет backoff и нет счётчика попыток в `pendingMedia.ts` (подтверждено: ни `backoff`, ни `attempts`,
  ни `nextRetry` в коде нет). Авто-flush триггерится по `online`, `socketReady`, реконнекту →
  мгновенные параллельные ретраи без паузы.
- Повторная заливка медиа в MinIO при каждом ретрае (нет кэша `UploadResult` в задании).
- FIFO не гарантирован: `flushOutbox` запускает задания параллельно, серверный ULID назначается в
  момент записи → быстрые подряд сообщения могут инвертироваться у получателя.
- Статус `delivered` отсутствует; ветка `SENT_VIA_SOCKET` может оставить сообщение в вечном `pending`.

### Медиа
- `media.routes.ts:34-43` — `Buffer.concat(chunks)`: весь файл (до 200 МБ) в RAM, затем temp-файл,
  затем `fs.readFile` обратно в буфер → кратное превышение размера файла в куче.
- Транскод (`transcode.ts` через `execFile` — event loop **не** блокируется, это плюс) и Whisper
  (`chat.service.ts`) выполняются инлайн в запросе без лимита параллелизма.
- Рассинхрон лимитов: nginx `client_max_body_size 500m` vs fastify multipart `200MB` vs per-type
  (image 20 / audio 30 / circle 50 / video 200 / document 100 МБ) — отказ происходит поздно, после
  полной загрузки в память.
- Orphan-файлы: нет GC для объектов MinIO без сообщения; нет lifecycle-политики.
- Расхождение `nginx/dev.conf:46` (`proxy_pass …/;` срезает префикс `/media`) vs `prod.conf:81`.

### Звонки
- `ringTimers` — `Map` в памяти инстанса (`calls.signaling.ts:65`) при включённом Redis adapter.
- `CALL_STATE_TTL_SEC = 4 часа` на RINGING-стейт → потерянный таймер = BUSY до 4 часов.
- Неатомарные переходы accept/decline (read-then-write вместо conditional update).
- TOCTOU busy-проверки: два одновременных invite проходят (`getUserActiveCall` → `saveState` разнесены).
- Нет обработки `iceConnectionState==='disconnected'` и нет `restartIce()` → смена сети рвёт звонок.

### Инфраструктура
- `getOnlineUserIds` → `redis.keys('presence:*')` (`presence.ts:23`), вызывается на **каждом**
  подключении (`socket.server.ts:238`).
- `user_online`/`user_offline` рассылаются глобально `io.emit` всем (`socket.server.ts:243` и др.).
- Scheduler без распределённого лока (нет `FOR UPDATE SKIP LOCKED` / SETNX — подтверждено грепом).
- Prisma connection pool не сконфигурирован; отдельные клиенты у core/realtime/scheduler.
- Нет graceful shutdown у core; realtime закрывается обрывно без `io.close()`/дренирования.

## 5. Потенциальные проблемы под нагрузкой

- **Реконнект-шторм** (деплой или массовый обрыв мобильных): каждый коннект → `KEYS presence:*`
  (O(N) блокировка Redis) + глобальный `io.emit` presence (O(N) фреймов) → O(N²) и лавинная
  деградация **всего** realtime (Redis общий для adapter/pubsub/presence/rate-limit).
- **Параллельные загрузки видео**: N×(до 200 МБ) в RAM на media-инстансе без `mem_limit` в compose
  → OOM-килл контейнера → обрыв всех активных загрузок.
- **Активные/большие чаты**: push офлайн-членам считается на каждое сообщение, `isOnline` в цикле
  (N round-trip в Redis), `fetchSockets()` (межинстансный запрос) на каждое новое сообщение.
- **Поиск по истории**: `ILIKE %q%` без GIN/pg_trgm → sequential scan по горячей таблице `messages`.
- **Connection pool**: при нескольких репликах суммарный пул Prisma превысит `max_connections=100`.

## 9. Race conditions (сводно)

1. **accept vs decline / accept на двух вкладках** (C-2): read-then-write без conditional update →
   финальный статус зависит от порядка двух независимых транзакций. **Fix:** `UPDATE … SET
   status='ACTIVE' WHERE id=? AND status='RINGING'` + проверка affected rows.
2. **Два одновременных invite (busy TOCTOU)** (H-2): `getUserActiveCall`→`saveState` разнесены.
   **Fix:** атомарный захват `SET call:user:<uid> <callId> NX` для обоих + partial unique index.
3. **Запись сообщения + публикация не в одной транзакции** (H-3): падение между commit и publish =
   записанное, но никем не уведомлённое сообщение. **Fix:** серверный outbox-паттерн или явная
   опора на pull-ресинк + ресинк по реконнекту для всех чатов.
4. **Параллельный flush outbox** (M-2): инверсия порядка. **Fix:** сериализация по `chatId`.
5. **`deliverToNewMembers` vs broadcast**: возможна двойная доставка `message_new` (спасает
   клиентский дедуп по `id`/`clientMessageId` — до пользователя дубль не доходит).
6. **Scheduler-реплики** (H-6): двойная выборка `sentAt:null` → двойной push.
7. **Идемпотентность отправки сделана правильно** (`@@unique([chatId, clientMessageId])` + обработка
   P2002) — дубли сообщений в БД исключены.

## 10. Проблемы масштабируемости

- **Single-instance / single-host деплой.** Код готов (Redis adapter + pub/sub), инфраструктуры нет:
  один контейнер каждой роли, статические DNS `core:3001`/`realtime:3002` в nginx, без балансировщика
  и sticky-сессий для WS. Один Node-процесс не вытянет десятки тысяч WS.
- **`KEYS`-presence** (C-3) — самый дешёвый высокоэффективный фикс (→ `SCAN`/`SET`/не слать полный снапшот).
- **Глобальные presence-бродкасты** (M-7) — O(N) на каждый коннект.
- **`fetchSockets()` на каждое сообщение** (межинстансный запрос ко всем нодам).
- **Connection pool** (H-7) — нужен PgBouncer + явный `connection_limit`.
- **Отсутствие очередей** для медиа/push/AI — тяжёлые задачи в синхронном пути.
- **MinIO/coturn одиночные** — SPOF хранилища; TURN привязан к хосту (`network_mode: host`).

## 11. Проблемы отказоустойчивости

| Падает | Текущее поведение | Чего не хватает |
|--------|-------------------|-----------------|
| core | `restart: unless-stopped` поднимет; нет graceful shutdown → активные запросы рвутся | `app.close()` по SIGTERM |
| realtime | Поднимется; все WS рвутся одномоментно → реконнект-шторм → C-3 | `io.close()` + дренирование, rolling rollout |
| Redis | Останавливается весь realtime; pub/sub-сообщения момента сбоя теряются | Sentinel/Cluster; Redis Streams для гарантий |
| Postgres | `maxRetriesPerRequest` исчерпается → 500; restart поднимет | HA/replica, PgBouncer |
| MinIO | Загрузка/раздача медиа недоступна | Распределённый режим / managed S3 |
| coturn | Звонки за NAT не устанавливаются | Кластер TURN, не `network_mode: host` |

Нет: circuit breakers, backoff-бюджетов на внешние вызовы (web-push/LLM/SMTP — только `Promise.allSettled`),
failover. Retry/дедуп есть только на клиентской отправке и на идемпотентности БД.

## 12. Производительность очередей

Выделенной системы очередей (BullMQ/RabbitMQ) **нет**. «Очереди» = клиентский outbox (IndexedDB) +
Redis pub/sub (fire-and-forget, не персистентный).

- Клиентский outbox: персистентный, переживает reload — ✅; но без backoff/лимита попыток (C-6) и с
  повторной заливкой файлов (C-7).
- Серверная доставка: pub/sub без подтверждений и без буфера — сообщения момента сбоя Redis теряются.
- Тяжёлые задачи (транскод/Whisper/AI/push) не имеют очереди вообще — выполняются в HTTP/socket-цикле.

**Рекомендация:** ввести BullMQ (Redis уже есть) для транскода, push-рассылки, AI и транскрипции;
для гарантированной доставки realtime рассмотреть Redis Streams с consumer-group.

## 13. Производительность WebSocket-системы

Сильные стороны: Redis adapter (кросс-инстанс), доставка через pub/sub (получатель на любом инстансе),
presence в Redis с TTL, идемпотентность.

Узкие места: `KEYS presence:*` на коннект (C-3), глобальный `io.emit` presence (M-7), `fetchSockets()`
на сообщение (M-2 инфра), push/AI синхронно в обработчике (M-6), `isOnline` в цикле, CORS `origin:'*'`
на сокете при строгом REST-CORS, нет graceful drain (H-8).

## 14. Производительность хранения сообщений

- Курсорная пагинация по ULID с `@@index([chatId, id])` — ✅ горячий путь ленты покрыт.
- Идемпотентность `@@unique([chatId, clientMessageId])` — ✅.
- Поиск `ILIKE %q%` без GIN/pg_trgm — 🔴 sequential scan (M-8).
- Системные/пин-сообщения без дедуп-ключа — двойной тап из двух вкладок создаёт два сообщения.
- Комментарий в схеме про «UUID v7» расходится с фактическим `ulid()` (косметика).

## 15. Производительность звонков

- Teardown WebRTC сделан корректно: треки `stop()`, senders, `pc.close()`, обнуление хендлеров
  (`webrtc.ts:314`) — **утечки PC на нормальном завершении нет**.
- Утечка возможна только в одном узком случае: `RTCPeerConnection` создаётся в конструкторе
  `CallEngine` до `await initLocalMedia`; при отказе доступа к микрофону движок не присваивается и
  pc не закрывается → утечка одного pc на каждый неудачный старт.
- TURN-креды временные (HMAC, RFC 5766) — ✅; но `total-quota`/`user-quota` не заданы.
- Группа: не функционирует (`CALL_GROUP_UNSUPPORTED`), mesh для N>2 не реализован (соответствует docs).

## 16. Рекомендации по исправлению (приоритизированный backlog)

2. **C-1:** cleanup-воркер для зависших звонков (`status IN (RINGING) AND createdAt < now()-45s`) +

3. **C-2:** conditional update переходов звонка (`WHERE status='RINGING'` + affected rows).
4. **C-5:** стримить upload → ffmpeg → MinIO без `Buffer.concat`; добавить `mem_limit`/`cpus` контейнерам.

11. **H-5:** выровнять лимиты (nginx ≈ backend+10%), проверять размер/тип **до** чтения тела.

13. **H-7:** PgBouncer + явный `connection_limit`, поднять `max_connections`.

## 17. Рекомендации по масштабированию

- Вынести Redis (Sentinel/Cluster), Postgres (replica + PgBouncer), MinIO (распределённый/managed S3) в HA.
- Несколько реплик `realtime`/`core` за L4/L7-балансировщиком; для WS — sticky по ip-hash или
  `transports:['websocket']` + Redis adapter (уже есть).
- Раздача медиа через presigned-URL / CDN напрямую из MinIO, без прокси через Node (`getPresignedUrl`
  уже реализован, но раздача идёт через прокси-роут). Учесть требование CDN origin Host в `server_name`.
- Очереди (BullMQ) для всех тяжёлых задач; масштабировать воркеры независимо.
- coturn — кластер, уйти от `network_mode: host`.

## 18. Рекомендации по мониторингу

- Метрики: число WS-соединений на инстанс, латентность Redis-команд (особенно presence), длина
  очередей BullMQ, p95 транскода/Whisper, RAM/CPU media-контейнера, Prisma pool utilization,
  `too many connections`, кол-во RINGING-сессий старше 60 с (ранний детектор C-1).
- Алерты: реконнект-шторм (rate connections), OOM-килл контейнера, рост orphan-объектов в MinIO,
  Redis latency p99, lag scheduler.
- Трейсинг пути сообщения: client → REST/socket → DB → pub/sub → получатель (для диагностики H-3).
- Sentry/логирование сбоя публикации после commit (для H-3).

## 19. Рекомендации по нагрузочному тестированию

- **WS-шторм:** k6/artillery — N тысяч одновременных коннектов + массовый одновременный реконнект
  (эмуляция деплоя); цель — поймать деградацию от `KEYS` (C-3) до и после фикса.
- **Отправка:** burst по десяткам сообщений в несколько чатов с эмуляцией плохой сети (latency/loss)
  — проверить FIFO (M-2), backoff (C-6), отсутствие дублей.
- **Медиа:** параллельные загрузки 50/100/200 МБ — замерить RAM media-контейнера (C-5), 504 по таймауту (H-4).
- **Звонки:** массовые invite/accept/decline с гонками и реконнектами сети — поймать C-1/C-2/H-1/H-2.
- **Scheduler:** запустить 2 реплики, проверить задвоение напоминаний (H-6).
- **БД:** профилирование `searchMessages` и ленты на большом объёме истории; мониторинг pool (H-7).

## 20. Финальная оценка готовности к продакшену

- **Закрытая бета / сотни одновременных пользователей:** условно готово **после** P0 по звонкам
  (C-1, C-2) и presence (C-3). Без них — частые инциденты «не могу звонить (занято)» и деградация
  realtime при реконнектах.
- **Десятки тысяч одновременных:** **не готово** до реализации горизонтального масштабирования
  (§17), очередей (§12) и HA Redis/PG/MinIO.
- **Сотни тысяч:** **не готово** — требует всего вышеперечисленного + нагрузочного теста с
  измеренными порогами (§19), CDN-раздачи медиа и SFU для групповых звонков.

**Сильные стороны, на которых можно строить:** идемпотентность отправки, персистентный outbox,
forward-sync, Redis adapter + pub/sub, корректный WebRTC-teardown, временные TURN-креды. Архитектурный
фундамент верный — основная работа в инфраструктуре, очередях и атомарности переходов состояния.
